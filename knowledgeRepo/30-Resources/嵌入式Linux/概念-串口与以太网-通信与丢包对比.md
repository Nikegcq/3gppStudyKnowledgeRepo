# 概念：串口与以太网 —— 通信模型与丢包原因对比

## 一句话

串口和以太网是两种**设计目标完全不同**的通信方式：串口追求简单、点对点、低成本，几乎不做可靠性设计；以太网是网络化、高速、带完整 TCP/IP 协议栈的组网方式。两者「丢包」的根源来自不同层面——串口几乎全在**软件（驱动/应用）与物理层**，以太网则把大部分工作交给了**硬件和协议栈**。

---

## 一、串口通信 vs 以太网通信

### 1. 基本定位

| 维度 | 串口（UART） | 以太网（Ethernet） |
|---|---|---|
| 类型 | 点对点、低速、简单 | 网络化、高速、复杂 |
| 拓扑 | 两个设备直连 | 多设备组网（交换机/路由器） |
| 典型速率 | 9600 bps ~ 几 Mbps | 10 Mbps ~ 100 Gbps |
| 传输单位 | 字节/字符 | 帧（Frame） |
| 协议层次 | 几乎没有协议栈 | 完整 TCP/IP 协议栈 |
| 硬件成本 | 极低 | 较高 |
| 距离 | 几米 ~ 几十米 | 100 米（双绞线）~ 几十公里（光纤） |

### 2. 协议层次对比

**串口：**

```
应用数据
   ↓
UART 硬件：起始位 + 数据位 + 校验位 + 停止位
   ↓
物理线（TX/RX/GND）
```

- 没有寻址、没有握手（除非用 RTS/CTS）、没有重传。
- 数据就是**裸字节流**，发送方写什么，接收方就收到什么（理想情况下）。

**以太网：**

```
应用数据
   ↓
TCP/UDP
   ↓
IP
   ↓
以太网帧（含 MAC 地址、CRC）
   ↓
PHY 芯片 → 双绞线/光纤
```

- 有寻址（MAC/IP）、有校验（CRC）、有重传（TCP）、有流控（TCP 窗口）。
- 数据被封装成**帧**，每层都有自己的头尾。

---

## 二、为什么串口容易丢包？

「丢包」在串口场景通常指：**接收方没有收到发送方发的某些字节，或者收到了错误字节**。根本原因可归为三类。

### 1. 没有协议层的可靠性保证

串口**本身不提供**：

- 重传机制
- 序号确认
- 流控（除非启用硬件流控）
- 错误恢复

一旦某个字节出错或丢失，**没有任何机制能发现并纠正**。以太网则不同：

- 以太网帧有 CRC，出错直接丢弃（但至少知道错了）。
- TCP 有序号 + ACK + 重传，丢了会补。
- 即使 UDP 不可靠，也有校验和能发现错误。

### 2. 接收方处理不及时（最常见原因）

这是嵌入式串口丢包的**头号原因**：

**现象：**

- 发送方以 115200 bps 连续发送，接收方 MCU 每收到一个字节触发一次中断。
- 如果中断处理太慢，或者中断被高优先级任务屏蔽，**下一个字节已经到达，而前一个还没被读走**。
- UART 硬件通常只有 **1~2 字节的接收缓冲**（如 AVR 的 UDR 只有 1 字节）。
- 新字节覆盖旧字节 → **溢出（Overrun）→ 丢包**。

**典型场景：**

| 场景 | 后果 |
|---|---|
| 中断里做了耗时操作（如 `printf`） | 后续字节来不及读 |
| 全局关中断时间过长 | 串口中断被延迟 |
| 高优先级中断频繁打断 | 串口中断得不到响应 |
| 波特率太高，MCU 主频太低 | 每个字节间隔太短 |
| 没有用 DMA 或环形缓冲 | 全靠中断逐字节处理 |

**以太网为什么不容易这样？**

- 网卡/PHY 有**硬件接收缓冲**（几 KB 到几十 KB）。
- 收到完整帧后才交给协议栈，不是逐字节中断。
- 有 DMA，CPU 不用管每个字节。

### 3. 物理层和时钟问题

串口是**异步通信**，没有单独的时钟线，靠双方约定的波特率采样：

- 发送方和接收方的波特率如果有偏差（晶振不准），采样点会逐渐偏移。
- 一帧 10 位（起始 + 8 数据 + 停止），偏差超过约 5% 就可能采错。
- 长线、干扰、地电位差会导致电平错误。
- 没有差分信号（RS-232 单端），抗干扰能力弱。

以太网：

- 有曼彻斯特编码或 4B/5B 等编码，**自带时钟恢复**。
- 差分信号（双绞线），抗共模干扰强。
- PHY 层有均衡、滤波。

### 4. 没有流控

串口默认**没有流控**：

- 发送方不知道接收方缓冲区满没满。
- 接收方处理不过来时，只能丢。
- 硬件流控（RTS/CTS）可以缓解，但需要额外线，且很多应用没启用。

以太网：

- TCP 有滑动窗口，接收方可以告诉发送方「慢点发」。
- 交换机有缓冲和背压机制。

## 三、串口丢包的典型排查方向

| 现象 | 可能原因 | 解决 |
|---|---|---|
| 高速连续收发丢字节 | 接收中断来不及处理 | 用 DMA + 环形缓冲 |
| 偶发丢字节 | 中断被屏蔽太久 | 缩短临界区，提高串口中断优先级 |
| 数据错乱 | 波特率不匹配 | 核对双方时钟、晶振 |
| 长距离通信丢包 | 干扰 / 电平不匹配 | 用 RS-485 / 差分、加屏蔽 |
| 大量数据丢包 | 无流控 | 启用 RTS/CTS 或加协议重传 |
| 特定字节丢失 | 校验/停止位配置不一致 | 核对数据位、校验位、停止位 |

## 四、总结对比

| 维度 | 串口 | 以太网 |
|---|---|---|
| 可靠性机制 | 几乎无 | CRC + ACK + 重传 |
| 接收缓冲 | 1~2 字节（硬件） | KB ~ MB 级 |
| 中断粒度 | 每字节一次 | 每帧一次 + DMA |
| 流控 | 可选，常不用 | TCP 窗口 + 交换机背压 |
| 时钟 | 异步，易漂移 | 编码自带时钟恢复 |
| 抗干扰 | 弱（单端） | 强（差分） |
| 丢包后 | 无法察觉 / 无法恢复 | 可检测、可重传 |

> **一句话：** 串口容易丢包，不是因为它「坏」，而是因为它**简单到没有做任何可靠性设计**——没有缓冲、没有流控、没有重传、没有时钟恢复。丢包的责任完全落在软件（驱动 / 应用层）身上。以太网则把这些工作交给了硬件和协议栈。

## 与工作的关联

- 与 [[概念-SPI总线与四种模式]] 同属「嵌入式总线 / 接口」主题：SPI 是同步（有时钟线）移位通信，串口是异步无时钟通信，两者对「时钟 / 采样」的要求正好相反。
- 串口调试口、RS-485 现场总线、以太网 PHY/MAC 驱动常出现在嵌入式 Linux 与 RTOS 项目中；协议栈承载可对照 [[学习-Linux-学习路线]]。
- 若与无线接入结合：以太网帧对应 L2 数据链路，串口多用于板内调试与外设控制。
